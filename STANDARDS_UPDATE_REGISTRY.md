# Standards Update Registry

**Version:** v1.3
**Date:** 2026-11-21
**Authors:** Tim Coulter (Red Hat) with Claude (Anthropic)
**Purpose:** Every framework this library implements tracks an upstream standard that
*will* change. This registry records what version we implement, how often the upstream
revises, and where to watch — so Rego gets regenerated when the standard updates instead
of drifting silently.

**Why this exists (the motivating incident):** on 2026-09-02, the CISA CPG module was
nearly written against v1.0.1 goal IDs — but CISA had shipped **CPG 2.0 in October 2025**
with a complete renumbering (old 2.H MFA became 3.F, three goals deleted, four added).
A one-fetch check caught it. This registry is that check, systematized.

**Machine-readable source of truth:** [`standards.yaml`](standards.yaml) lists every framework key with the
standard, the exact version the module implements (each version is tied to literal text in the module, and
`make check-standards` fails when the two drift apart or a key has no entry), the publisher and a release-check
method. `python3 scripts/check_standard_releases.py` runs those checks over the network (NIST OSCAL catalog
JSON, GitHub releases/commits, DISA STIG zip names on dl.dod.cyber.mil, eCFR amendment dates, CIS monthly
update posts, version strings on publisher pages) and reports `newer`, `review` or `failed`; sources with no
feed are listed as `manual`. This document keeps the cadence, context and notes a human needs.

## Update process

1. **Monthly sweep** (scheduled): run `python3 scripts/check_standard_releases.py --json standards-report.json`
   (the monthly workflow does this), then check the `manual` rows' watch URLs by hand. A `failed` row is not
   "up to date": fix the source or check it by hand.
2. **On a new release:** open an issue titled `update: <framework> <old> → <new>` with the
   changelog link. Triage: renumbering/new controls → regenerate the module; editorial →
   bump the version comment only.
3. **Regeneration rule:** new benchmark versions get a **new directory** (existing
   convention — do not mutate the old version). Framework modules revise in place with the
   version pinned in the header and this registry updated in the same PR.
4. **Clearing a finding** (same PR as the triage, so the next run does not flag it again): `ecfr` → raise
   `checked_through` to the amendment date reviewed; `page_regex` → add the reviewed value to `known` (or bump the
   module and its `version`); a family (`cis`, `disa`) → raise `checked_against`; `github_commit` → new sha in
   `version` (or a later `since`); `github_release` / `oscal_catalog` / DISA zips → only a module update with the new
   `version` and `literal` clears them.
5. **Rows marked "verify"** carry cadence/next-expected values from general knowledge, to
   be confirmed on their first sweep.
